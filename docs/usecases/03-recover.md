# 用例 03：找回账户/密钥（Recover）

> 生命周期位置：横切流程（密钥丢失、换机、安全事件） ｜ 参与者：玩家、guardians（第二 passkey / 邮箱 / 运营托管）
> 前置条件：注册时已配置恢复监护人（RecoveryModule 默认引导开启）
> 成功保证：**账户及全部资产（Fighter/段位/奖金/$ARENA）零损失**；恢复完成后旧密钥全部失效
> 上游依据：技术 §3.1（RecoveryModule）、§4.5、§9.1（威胁表"账户丢失"行）

## 0. 核心认知：没有"助记词"可丢

本系统没有种子短语。账户 = 链上 Safe 合约，passkey 只是"开门钥匙"之一。**换钥匙不换房子**——段位、Fighter、奖金全部挂在账户地址上，与任何一把私钥无关。

## 1. 触发与入口

- 手机丢失/刷机 → passkey 没了
- 换新设备，旧设备不可用
- 怀疑密钥泄露 → 主动轮换

## 2. 主流程

### 场景 A：还持有备用 passkey（ guardian = 第二 passkey，存在 iCloud/另一设备）

```
① 新设备登录页面 → 「使用其他钥匙」
② 验证备用 passkey（系统生物识别）
③ 一笔 UserOp（备用 passkey 签名，L2）：
   RecoveryModule.rotateKeys [
     addPasskey(新 passkey 公钥)
     removePasskey(丢失的旧 passkey)
     revokeAllSessions()          ← 所有比赛会话密钥、代打 operator key 全部吊销
   ]
④ 完成：新 passkey 即主钥匙，回到用例 02 登录
   耗时 ~1 分钟，1 次签名
```

### 场景 B：自有 passkey 全部丢失 → Social Recovery

```
① 新设备 → 「发起社交恢复」→ 提交账户地址 + 新 passkey 公钥
② 收集 guardian 签名：
     - 邮箱 guardian：邮件验证码（验证"是这个人在申请"）
     - 运营托管 guardian：风控审核（设备指纹/行为分，防抢账户）
   达到监护人阈值（如 2/3，参数待定）
③ 链上进入恢复延时窗口（如 24–48h，参数待定）
   → 期间原密钥仍可"紧急叫停"（若本人发现是被盗恢复）
④ 窗口结束 → 恢复生效：
     - 新 passkey 挂载为 owner
     - 全部会话密钥/代打密钥自动吊销
     - 事件 RecoveryCompleted 上链，可审计
⑤ 用新 passkey 登录（用例 02）
```

## 3. 状态与数据变化

| 对象 | 之前 | 之后 |
|---|---|---|
| 账户 owner 密钥 | 丢失的 passkey | 新 passkey |
| 会话/代打密钥 | 可能仍"有效" | **全部吊销**（安全属性：旧钥匙即使被捡到也作废） |
| Fighter / 段位 / 奖金 / $ARENA | 挂在账户上 | **不变，零损失** |
| 进行中对局 | — | 棋钟照走（见 §5） |

## 4. 体验要点

- 场景 A：1 次签名、~1 分钟、Gas 由 Token 代付或运营赞助（待定）
- 场景 B：延时窗口内进度条 + 提前完成条件（若保留 guardian 全签可缩短，参数待定）

## 5. 异常与边界

| 情形 | 处理 |
|---|---|
| 恢复期间有进行中对局 | 棋钟不暂停 → 可能超时判负。**损失上限 = 一局入场费**（技术 §9.1 同一风险面结论）；代打 Second 可在吊销前继续应战（其密钥恢复后才失效——事实上起到了"护盘"作用，但需风控确认非攻击者委托） |
| 攻击者发起虚假恢复（抢账户） | 三重防线：邮箱验证 + 运营风控审核 + 延时窗口内原密钥可叫停 |
| guardians 串通 | 运营托管 guardian 有独立风控，不与邮箱同渠道；恢复事件全上链可审计 |
| 邮箱也丢了 | 运营托管 guardian 人工申诉通道（KYC 级，慢路径） |
| passkey 泄露但账户未丢 | 主动走场景 A 轮换（rotateKeys 即刻吊销旧钥） |

## 6. 权限与安全

- 签名层级：恢复操作本身 = **L2**（guardian 签名聚合后执行）
- 恢复是敏感操作：**永远不可由会话密钥/代打密钥触发**
- 与敏感操作同级的信任假设：guardian 阈值 + 延时窗口是账户安全的最后防线，参数需安全评审

## 7. 规格待定项

1. guardian 阈值与延时窗口具体参数（建议 2/3 + 24h 起评）
2. 恢复操作的 Gas 承担方（建议运营赞助，防止用户"卡死在门外"）
3. 恢复窗口内进行中对局的赛制处理（超时判负 vs 冻结棋钟——冻结需改合约，倾向维持现状并在 UX 明示）
4. 代打 Second 在恢复窗口期的权限边界（风控规则）
